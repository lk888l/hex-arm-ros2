## ROS 链路排查记录

独立 Rust/CAN 固定顺序可运行，但最初接通真实 ROS 执行发现：

1. bridge 的 Zenoh 状态回调等待管理事务锁，导致激活 RPC 的响应也被阻塞。
   回调门禁改用短数据锁；仍检查新鲜 ACTIVE 状态及独占会话。
2. Python 多线程执行器在连续 100 Hz 流量下出现大于 100 ms 的调度延迟。
   独立采样中 C++ 指令约 100 Hz、最大间隔约 10.5 ms，原始 Zenoh 状态约
   100 Hz，延迟集中在 bridge。使用模拟电机也可复现。
   单独缩短 GIL 切换间隔或插入让出不足以解决全部真机情况，最终为 100 Hz
   指令/状态增加独立 SingleThreadedExecutor；管理服务留在生命周期节点。
3. 硬件插件在激活失败后直接析构可遗留可 join 的线程；增加析构与 shutdown
   清理。立即 configure/shutdown 测试又发现 cancel 先于 spin 的竞态，
   改用停止标志和有界 spin_once。ROS context 关闭或服务消失时中止待处理
   服务等待；停止和 error recovery 不再重新等待服务发现。
4. 真实 JTC 增加 position+velocity 指令接口，把轨迹速度传到电机 PD；
   mock/gz 仍保留原配置。Rust 的目标流与使能/失能共用模式锁，避免主动失能
   与最后一帧 set_targets 交错而误报传输故障。
5. 插值算法把带非零端点速度的可行时长错误地当作单调区间。确定性反例中，
   本来满足 0.1 rad/s、0.1 rad/s² 的 10 ms 匀速段被拉长为 2.989966440 秒。
   新实现求三次曲线速度/加速度边界的根，在全部关节的共同可行时长中选取；
   每次仍用连续时间极值验证限幅。新增短区间、六轴抖动和随机密集比较测试。
6. 新增使能前指令发布端 DDS 匹配检查，防止反馈已到、指令端尚未匹配就
   开始 100 ms 看门狗。只有新鲜反馈、没有指令接收端时，不调用使能服务。

故障试验由 Rust 看门狗执行确认失能。上述调试没有增大 100 ms 指令/反馈超时，
没有放宽 ROS 轨迹容差，也没有改变严格碰撞矩阵。
