## 完整链路采集

以下为第二次启动后约 5 秒健康保持窗口，包含缓存查询和刷新拒绝，采集丢弃记录数为 0。

|---|---:|---:|---:|
| Python 收到指令 → Rust 接受 | 501 | 0.270 ms | 0.288 ms |

| 邮箱写入 → CAN 入队开始 | 501 | 2.423 ms | 2.563 ms |

这段短测只能说明此保持场景，不能作为普遍性能承诺或优化前后对比。

## 长时间 mock 基线

三轮独立基线各预热 30 秒、采样 300 秒，使用隔离 ROS domain 73 和 Zenoh endpoint 7459。
夹具只包含 ROS 指令源、Python bridge、Rust mock 驱动，不包含 C++ 插件和 CAN。
mock 控制频率为 1000 Hz，状态发布为 100 Hz；真机 profile 控制频率为 500 Hz，二者不能直接比较总链路时延。
三轮各接受 30,000 个指令，共 90,000 个，均未锁存故障，trace 丢弃数均为 0。
完整数据保留于 `.tmp-optimization/transport-baseline/`。

| 轮次 | Python 接收 → Rust 接受 p99 / max | Rust 接受 → 控制消费 p99 / max | Rust 接受最大连续空窗 |
|---|---:|---:|---:|
| 1 | 0.318 / 4.703 ms | 1.073 / 3.351 ms | 17.413 ms |
| 2 | 0.253 / 0.470 ms | 1.079 / 1.384 ms | 11.539 ms |
| 3 | 0.239 / 0.446 ms | 1.078 / 1.230 ms | 10.895 ms |

指令源至 Python 接收的 p99 分别为 0.324、0.273、0.332 ms；第一轮最大值为 7.808 ms。
控制周期最大连续空窗分别为 4.316、1.956、2.028 ms。
Python 收到反馈至 ROS 发布的匹配样本 p99 为 7.858、8.872、9.894 ms，呈现独立周期的相位等待。
第三轮 30,000 个已接收反馈中有 5,819 个未匹配到后续发布，符合只转发最新状态时的覆盖统计；
不能将“trace 没有丢记录”解释为“每个反馈样本都被转发”。
这些是当前实现的基线，尚无同环境优化前对照，不宣称时延改善。

## 后续优先级

本轮测量支持继续维持当前指令链路：保持场景中 Python 到 Rust 接受的 p99 约 0.27 ms，
正向时延主要受控制和发送周期影响。反馈端的两个周期任务存在可见相位等待，
可在明确预算后另行比较反馈发布调度与 C++ 直连方案。

优先单独处理真机速度反馈或闭环动态问题，再定义来源时间戳新鲜度、独立控制进度保护、
旧周期故障条件提交及热替换身份失效规则。MoveIt 升级必须继续跑启动门控、执行、取消和退出契约。
